**Change request:** Interview Schedule Management CRUD. The `schedule` module already implements
full CRUD (create, read list, read one, update, delete) with coordinator/admin RBAC. This session
extends the "add new schedule" payload with the three fields from the spec that do not yet exist:
Batch Code, Examination Type (Onsite/Online), and Proctor/Interviewer.

---

## Spec-to-code mapping (what already exists)

- Sponsor -> `schedule.sponsorship_id` FK (the sponsorship carries the sponsor).
- Batch -> `schedule.batch_no`.
- Type of Schedule (Exam/Interview) -> `schedule.schedule_type` enum, values `TEST` / `INTERVIEW`.
  UI label "Exam" maps to stored `TEST`.
- Specific Date + Time Start/End -> `schedule.start_date` / `schedule.end_date` (two DateTimes; the
  FE composes a date with start/end times). `end_date > start_date` is already validated.
- Limit (Examinees/Interviewee) -> `schedule.schedule_quota` (Int, min 1).
- Building/Room -> `schedule.location`.

## Decisions Made

- **Add three new fields to the existing schedule CRUD:**
  - `batch_code` - free-text code the coordinator types on the add-schedule form. New column
    `batch_code String? @db.VarChar(255)`. Independent of `batch_no`. Request field `batchCode`.
  - `examination_type` - modality, applies to EVERY schedule (exam and interview). New Prisma enum
    `examination_type { ONSITE ONLINE }`, column `examination_type examination_type?`. Request field
    `examinationType`.
  - `proctor_interviewer` - single free-text name of the proctor/interviewer. New column
    `proctor_interviewer String? @db.VarChar(255)`. Request field `proctorInterviewer`.
- **Nullable columns, required at the API layer.** All three columns are DB-nullable so the additive
  migration needs no default/backfill on existing schedule rows; the create/update validator makes
  them required for new schedules. Legacy schedules read back null.
- **`examination_type` is unconditional.** Required regardless of `scheduleType`; no cross-field
  rule tying it to TEST vs INTERVIEW.
- **Enum label mapping stays at the FE.** The UI shows "Exam" while the stored value is `TEST`; no
  backend rename. Documented so QA does not treat it as a defect.
- **Validation lives in `validateSchedulePayload`** (shared by create and update), next to the
  existing `scheduleType` / `location` / `scheduleQuota` validators.
- **Bug 1 (by-id `scheduleId` destructure) will be fixed in the schedule TDD pass** - it is on the
  critical path for functional update/get-one/delete. **Bug 2 (list search on non-string columns)
  is deferred** and documented separately. Both are recorded in
  `docs/bugs/schedule-known-bugs-2026-07-09.md` (tracked in markdown, not GitHub).

## Constraints Identified

- The `schedule` model is at `schema.prisma:462-478`; `schedule_type` enum at `:581-584`.
- `validateSchedulePayload` (`validation.ts:942-987`) already enforces: sponsorshipId exists,
  batchNo exists for that sponsorship, scheduleType in [TEST, INTERVIEW], location/quota/startDate/
  endDate required, and end after start. New validators slot into this same array.
- `ScheduleRequest` / `ScheduleResponse` / `ScheduleModified` types are at `types.ts:634-668` - all
  three need the new fields; `ScheduleModified` uses snake_case for the Prisma read shape.
- Message strings must be added to `utils/constant.ts` (VALIDATION_MESSAGES), not inlined.
- Enum column note: adding a Prisma enum column to MySQL creates an `ENUM('ONSITE','ONLINE')`; keep
  it nullable so existing rows remain valid without a default.
