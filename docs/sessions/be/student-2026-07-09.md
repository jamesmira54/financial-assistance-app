**Change request:** In student information, allow only one emergency contact (remove the
second contact), and add a user-inputted relationship field to that single emergency contact.

---

## Decisions Made

- **Collapse to one emergency contact.** Stop reading/writing the second contact
  (`emergency_contact_name2`, `emergency_contact_number2`) everywhere in code.
- **Add `emergency_contact_relationship`** as a free-text `VARCHAR(255) NULL` column. Free text,
  not an enum, because the value is user-inputted. TS field name: `emergencyContactRelationship`.
- **Non-destructive-first migration.** Migration adds `emergency_contact_relationship` and code
  stops referencing `*_2`. The `*_2` columns are NOT dropped in this migration - they are dropped
  in a later migration only after confirming no row depends on them. Avoids irreversible data loss.
- **Validation:** `emergencyContactRelationship` is optional, mirroring the existing optional
  pattern for `emergencyContactName` / `emergencyContactNumber` in `middleware/validation.ts`.
- **Keep the code's `emergencyContact*` naming convention.** Swagger uses different names
  (`emergencyFullName` / `emergencyMobileNumber` / `emergencyRelationship`); swagger will be
  corrected to match the code rather than renaming the DB columns, types, and converter.

---

## Constraints Identified

- Emergency contact fields today live as flat columns on the student table
  (`prisma/schema.prisma:133-136`), not a separate relation - the change is column-level, no new table.
- `emergencyContactName2` and `emergencyContactNumber2` are declared **required** on the Detail
  response type (`utils/types.ts:439-440`). Removing them is a breaking response-contract change,
  not just an internal cleanup.
- Swagger (`docs/swagger.yml:4298-4306`) already documents a single emergency contact with a
  relationship (`emergencyFullName` / `emergencyMobileNumber` / `emergencyRelationship`), confirming
  the single-contact-with-relationship design is the intended end state - the code simply had not
  caught up.
- All message strings must be added to `utils/constant.ts` (VALIDATION_MESSAGES), not inlined.
